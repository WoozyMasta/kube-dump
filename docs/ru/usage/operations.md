# Операционные сценарии

Здесь собраны практические рекомендации
по организации и эксплуатации бекапов kube-dump.

## Несколько профилей

В одном кластере можно запускать разные профили с разным расписанием.
Например, один профиль выбирает пространства имён `dev-*` и запускается часто,
а другой выбирает `test-*` и запускается реже.

Оба запуска могут использовать один каталог:

```shell
kube-dump resource save dir ./backup --profile ./profiles/dev.yaml
kube-dump pvc save dir ./backup --profile ./profiles/dev.yaml
kube-dump image save dir ./backup --profile ./profiles/dev.yaml
```

Для профиля `test` меняется только файл профиля:

```shell
kube-dump resource save dir ./backup --profile ./profiles/test.yaml
kube-dump pvc save dir ./backup --profile ./profiles/test.yaml
kube-dump image save dir ./backup --profile ./profiles/test.yaml
```

Без `--prune` такие запуски дополняют общий результат:
ресурсы и образы не удаляются из-за того, что их не выбрал другой профиль.
PVC разных пространств имён также сохраняются в разные подкаталоги.

Если независимые расписания могут выполняться одновременно,
учитывайте правила из раздела [Конкурентные запуски][].

> [!CAUTION]
> Не используйте `--prune` в независимых запусках с одним каталогом.
> Профиль `dev` может удалить результаты профиля `test`,
> если его запуск завершится позже.

## Несколько кластеров

Обычно каждому кластеру задают собственный каталог.
Это самый простой вариант:
данные разных кластеров не смешиваются,
все три типа бекапа имеют единый корень кластера.

```text
backup/
├── cluster-a/
│   ├── resources/
│   ├── volumes/
│   └── images/
└── cluster-b/
    ├── resources/
    ├── volumes/
    └── images/
```

Пример команд для `cluster-a`:

```shell
kube-dump resource save dir ./backup/cluster-a
kube-dump pvc save dir ./backup/cluster-a
kube-dump image save dir ./backup/cluster-a
```

Если в разных кластерах используются одинаковые образы,
каталог образов можно вынести в общий корень.
OCI layout хранит содержимое по digest,
поэтому общие слои будут переиспользованы и не займут место повторно.

```text
backup/
├── cluster-a/
│   ├── resources/
│   └── volumes/
├── cluster-b/
│   ├── resources/
│   └── volumes/
└── images/
```

> [!CAUTION]
> Общий корень здесь используется только для образов.
> Не складывайте в него ресурсы и PVC разных кластеров,
> даже если сейчас каждый профиль выбирает уникальное пространство имён.
> Такой запуск технически отработает, но ресурсы уровня кластера,
> одинаковые пространства имён и PVC или изменение профиля
> впоследствии могут привести к перезаписи данных.
>
> Пространство имён не является границей изоляции между кластерами.

В этом варианте команды для образов используют `./backup`:

```shell
kube-dump image save dir ./backup
```

В S3 тот же принцип выражается разными префиксами
для ресурсов и PVC и общим префиксом для образов.
При раздельных кластерах не смешивайте их ресурсы или PVC в одном префиксе.

Если запуски для разных кластеров могут пересекаться по времени,
применяются те же правила из раздела [Конкурентные запуски][].

## Конкурентные запуски {#concurrent-runs}

Если два процесса одновременно пишут в один каталог или один S3-префикс,
результат зависит от типа данных.

* Для локальных образов второй `image save dir` ждёт,
  пока первый закончит работу.
  Это защищает общий OCI-каталог от одновременной записи.
* Для ресурсов действует такая же блокировка.
  В разные каталоги ресурсов можно писать одновременно.
* PVC разных объектов можно сохранять одновременно,
  если их наборы не пересекаются.
  Два запуска для одного PVC одновременно лучше не использовать:
  они могут одновременно менять одни и те же файлы.
* Между машинами общей файловой блокировки нет.
  Для S3 `image save` читает текущий индекс и при публикации проверяет,
  что его никто не изменил.
  Если другой процесс успел сохранить изменения, второй запуск
  завершится ошибкой конфликта и не затрёт уже опубликованный индекс.
* `image save s3` объединяет ссылки в общем OCI-индексе,
  но не удаляет старые blobs.

Локальные блокировки используют пустые файлы-маркеры
`.kube-dump-resource-writer-*.lock` и `.kube-dump-image-writer-*.lock`.
Они остаются в родительском каталоге после завершения команды;
сама блокировка хранится в дескрипторе файла и при завершении снимается.
Если запущенных процессов `kube-dump`, работающих с этими назначениями, нет,
файлы-маркеры можно удалить вручную.

> [!NOTE]
> Наличие `.lock`-файла не означает, что назначение сейчас заблокировано.
> Не удаляйте его во время работающего `kube-dump`:
> это может нарушить защиту от конкурентной записи.

## Очистка старых результатов

В `resource save` и локальном `image save`
опция `--prune` включает деструктивный режим.
После успешного сохранения kube-dump удаляет то,
чего больше нет в текущей выборке.

Для `resource save s3` результат также строится по текущей выборке,
но старые поколения удаляются с задержкой:
текущее и предыдущее поколение сохраняются для читателей.

Это позволяет убрать данные,
которые были удалены в кластере после предыдущего запуска.

> [!CAUTION]
> Используйте `--prune` только для одного отдельного бекапа
> со стабильной (не динамической) конфигурацией.
> В целевой каталог не должны писать другие профили, кластеры или расписания,
> а пространства имён и селекторы не должны меняться между запусками.
>
> Иначе очередной запуск удалит результаты,
> которые не входят в его текущую выборку.

Не размещайте произвольные файлы внутри управляемых подкаталогов `resources/`,
`volumes/` и `images/`, если их жизненный цикл должен отличаться от бекапа.
Для собственных файлов используйте соседний каталог верхнего уровня.
