# Данные PVC

Команда `pvc` сохраняет содержимое `PersistentVolumeClaim`.

Каждый PVC хранится отдельно в виде сжатого архива.
Поэтому данные томов можно сохранять с другой частотой
и хранить дольше или меньше, чем YAML.

Полный список параметров находится в [справочнике команд](../../cli.md#pvc).

## Обычное сохранение

```shell
kube-dump pvc save dir ./backup
```

Чтобы ограничить работу одним пространством имён, укажите его:

```shell
kube-dump pvc save dir ./backup --namespace production
```

Чтобы выбрать PVC по имени или маске, передайте один или несколько флагов:

```shell
kube-dump pvc save dir ./backup --pvc postgres-data --pvc 'redis-*'
```

## Как хранятся копии

Для каждого PVC создаётся отдельная копия с отметкой времени.

Например, следующий профиль выбирает PVC из `production` по маске имени:

```text
volumes/
  production/
    postgres-data/
      20260904T010203Z/
        data.tar.zst
        metadata.yaml
```

По умолчанию сохраняются последние пять копий каждого PVC.

Чтобы изменить число сохраняемых копий, укажите другое значение `--keep`:

```shell
kube-dump pvc save dir ./backup --keep 10
```

Чтобы не удалять старые копии, установите `--keep 0`:

```shell
kube-dump pvc save dir ./backup --keep 0
```

## Формат архива

Каждая копия содержит `metadata.yaml` и один сжатый поток данных.
В метаданных записаны формат, стратегия, сжатие, несжатый размер,
SHA-256 и состояние шифрования. `sizeBytes` — это несжатый размер.

Архив сохраняет обычные файлы и каталоги, относительные символические ссылки,
права доступа, числовые UID/GID и время изменения.
Расширенные атрибуты, ACL, разреженные файлы, топология жёстких ссылок,
устройства и другие специальные файлы не сохраняются.
Файлы с несколькими жёсткими ссылками отклоняются,
а Windows-агент не может восстановить ненулевые числовые UID/GID
и не гарантирует полное сохранение битов POSIX-прав.

Перед записью целевого PVC проверяется весь архив.
После начала распаковки восстановление
не является транзакцией и уже записанные данные не откатываются.
При восстановлении из локального каталога
используется временная копия закодированного архива,
поэтому во временном каталоге должно хватать места для него.
Helper проверяет и распаковывает поток,
не создавая в `/tmp` отдельную расшифрованную копию размером с PVC.

## Стратегия snapshot-copy

Это основной способ и значение по умолчанию.

```shell
kube-dump pvc save dir ./backup --strategy snapshot-copy
```

Схема работы:

```text
исходный PVC
  -> VolumeSnapshot
  -> временный PVC из снимка
  -> временный Pod
  -> архив
```

Плюс этого способа в том,
что kube-dump читает отдельную копию состояния на момент снимка,
а не живой том приложения.

> [!IMPORTANT]
> Для работы нужны CSI-снимки и соответствующие права в Kubernetes.

Временный вспомогательный Pod использует образ из текущей версии.
По умолчанию применяется `IfNotPresent`.
Если образ был обновлён под тем же тегом, задайте политику `Always`:

```shell
kube-dump pvc save dir ./backup --image-pull-policy Always
```

Путь к образу и исполняемому файлу вспомогательной программы
можно переопределить через `--image` и `--helper-binary-path`.
У вспомогательной программы есть эфемерный `/tmp` для небольших runtime-файлов,
но проверка и распаковка не сохраняют в нём расшифрованный архив размером с PVC.

Если нужно выбрать класс снимков явно, укажите его имя:

```shell
kube-dump pvc save dir ./backup --snapshot-class csi-snapshots
```

## Стратегия pod

Если кластер не поддерживает снимки или они недоступны,
используйте стратегию `pod`:

```shell
kube-dump pvc save dir ./backup --strategy pod
```

В этом случае временный Pod читает исходный PVC напрямую.

> [!WARNING]
> Для активно изменяемых данных этот способ менее надёжен,
> потому что приложение может продолжать запись во время копирования.
> Для баз данных и похожих нагрузок лучше использовать `snapshot-copy`,
> если хранилище его поддерживает.

## Сохранение в S3

```shell
kube-dump pvc save s3 --s3-uri s3://backup/prod/
```

При работе с S3 временный Pod может отправлять архив напрямую в хранилище.
Это особенно важно для больших томов:
данные не проходят через процесс kube-dump.

> [!IMPORTANT]
> Поэтому S3 должен быть доступен из кластера.

Если внутри кластера S3 доступен по другому адресу, передайте этот адрес:

```shell
kube-dump pvc save s3 --s3-uri s3://backup/prod/ \
  --s3-pod-endpoint http://seaweedfs.storage.svc:8333 \
  --s3-insecure
```

## Ограничение размера

Слишком большие копии можно запретить ограничением размера:

```shell
kube-dump pvc save dir ./backup --max-size 500GiB
```

Можно также задать общий предел для всех PVC одного пространства имён:

```shell
kube-dump pvc save dir ./backup --max-namespace-size 2TiB
```

## Отбор через профиль

Например, следующий профиль выбирает PVC из `production`:

```yaml
apiVersion: kube-dump/v2
kind: Profile

metadata:
  name: production
  description: Production PVC backup

resources: {}

pvc:
  selection:
    namespaces:
      - production
    names:
      - 'postgres-*'
      - 'redis-*'
```

Можно использовать также метки и аннотации.

Полный формат: [справочник профиля](../../profile.md#pvcpolicy).

## Шифрование

Архивы PVC шифруются AGE. Чтобы включить шифрование при сохранении,
передайте открытый ключ:

```shell
kube-dump pvc save dir ./backup --recipient age1...
```

Существующий архив тоже можно зашифровать отдельной командой:

```shell
kube-dump pvc encrypt data.tar.zst data.tar.zst.age --recipient age1...
```

Расшифруйте архив командой:

```shell
kube-dump pvc decrypt data.tar.zst.age data.tar.zst --identity ./age-key.txt
```

Подробнее: [Шифрование](encryption.md).

## Просмотр и распаковка

Посмотрите список локальных копий:

```shell
kube-dump pvc inspect dir ./backup
```

Посмотрите список копий в S3:

```shell
kube-dump pvc inspect s3 --s3-uri s3://backup/prod/
```

Распакуйте архив в каталог:

```shell
kube-dump pvc extract ./data.tar.zst ./restored
```

kube-dump восстанавливает файлы в каталог, но не создаёт PVC автоматически.

## Восстановление в PVC

Целевой PVC должен быть создан заранее.
Источник и цель указываются отдельно,
поэтому данные можно восстановить в другом пространстве имён или PVC:

```shell
kube-dump pvc restore dir ./backup \
  --pvc production/postgres-data \
  --target-pvc recovery/postgres-data
```

> [!IMPORTANT]
> Целевой PVC должен быть в состоянии `Bound`,
> использовать режим `Filesystem`, не использоваться Pod'ом
> и иметь ёмкость не меньше размера распакованного архива.

Для `merge` это только минимальная проверка:
уже занятое место внутри тома отдельно не учитывается.
Перед проверкой и записью kube-dump получает Kubernetes Lease,
привязанный к целевому PVC.
Это не даёт двум запускам одновременно восстанавливать данные
в один и тот же PVC, но не останавливает рабочие Pod.
Проверка использования PVC всё равно выполняется отдельно.

По умолчанию `empty-only` откажется писать в непустой целевой PVC.
Для явного выбора поведения доступны `merge` и `replace`:

```shell
kube-dump pvc restore dir ./backup \
  --pvc production/postgres-data \
  --target-pvc recovery/postgres-data \
  --existing merge
```

> [!CAUTION]
> `replace` удаляет существующие записи в корне целевого PVC перед распаковкой.
> При ошибке во время потока уже записанная часть автоматически не откатывается.

По умолчанию выбирается последняя копия.
Конкретную версию можно указать через `--revision 20260904T010203Z`.

Для источника в S3 используется аналогичная команда:

```shell
kube-dump pvc restore s3 \
  --s3-uri s3://backup/prod/ \
  --pvc production/postgres-data \
  --target-pvc recovery/postgres-data
```

Зашифрованная копия требует `--identity` и расшифровывается потоково.
Команда не останавливает рабочую нагрузку.
Для восстановления создаются временные helper Pod и Kubernetes Lease;
при необходимости для S3 также создаются временные Secret,
которые удаляются после завершения операции.

Непосредственно перед созданием helper Pod целевой PVC проверяется повторно.
Его UID должен совпадать с UID на первом этапе,
а сам PVC должен оставаться в состоянии `Bound`, в режиме `Filesystem`,
иметь достаточный размер и не использоваться работающим Pod.

Проверка архива отклоняет архивы более чем с 1 000 000 записями.
Это ограничение защищает от повреждённых архивов и не ограничивает размер PVC.
При массовой ошибке бекапа сохраняются подробности не более чем для восьми PVC,
а число скрытых подробностей сообщается отдельно.
