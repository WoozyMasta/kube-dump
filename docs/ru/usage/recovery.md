# Восстановление

kube-dump не пытается быть системой восстановления Kubernetes.

Он сохраняет данные в обычных форматах и даёт их прочитать обратно:

* ресурсы - YAML;
* образы - OCI Image Layout;
* PVC - сжатые архивы файловой системы.

Дальше используются обычные инструменты Kubernetes,
контейнерных реестров и самих приложений.

Такой подход оставляет восстановление явным:
kube-dump не скрывает создание PVC, изменение образов,
запуск рабочих нагрузок или миграцию данных одной командой восстановления.

## С чего начать

Перед восстановлением полезно сначала посмотреть, что именно сохранилось.

Сначала проверьте сохранённые ресурсы:

```shell
kube-dump resource inspect dir ./backup
```

Затем проверьте сохранённые копии PVC:

```shell
kube-dump pvc inspect dir ./backup
```

После этого проверьте сохранённые образы:

```shell
kube-dump image inspect dir ./backup
```

Для копии в S3 используются соответствующие варианты `inspect s3`.

Если данные зашифрованы, заранее подготовьте нужные AGE-ключи.

## Совместимость форматов

Сохранённые данные содержат метаданные, необходимые для проверки и чтения:
архивы PVC используют `metadata.yaml`, образы — стандартный OCI Image Layout,
а бекапы ресурсов — манифест владения.
Сохраняйте эти файлы вместе с данными
и используйте совместимую версию kube-dump v2 при переносе или восстановлении.
Текущий формат v2 рассчитан на использование с v2 версией kube-dump.
При переносе архива или бекапа
не удаляйте и не подменяйте версионируемые метаданные молча.

## Обычный порядок восстановления

Для полного окружения чаще всего удобен такой порядок:

1. Подготовить новый кластер и хранилище;
1. Опубликовать сохранённые контейнерные образы;
1. Подготовить YAML ресурсов;
1. Создать PVC, но не запускать приложения,
   которые сразу начнут с ними работать;
1. Вернуть данные в PVC;
1. Применить или включить рабочие нагрузки;
1. Проверить состояние приложений.

Это не обязательный порядок для любого Kubernetes-кластера,
но он хорошо подходит для большинства случаев
аварийного восстановления и переноса.

Главный принцип восстановления:
сначала вернуть зависимости и данные, а уже потом запускать приложения.

## Ресурсы Kubernetes

Сохранённые ресурсы можно получить как обычный поток YAML:

```shell
kube-dump resource cat dir ./backup > resources.yaml
```

Если отдельные поля были зашифрованы:

```shell
kube-dump resource cat dir ./backup \
  --identity ./age-identity.txt > resources.yaml
```

После этого проверьте полученный файл:

```shell
kubectl diff -f resources.yaml
```

Если содержимое корректно, примените его к кластеру:

```shell
kubectl apply -f resources.yaml
```

Для серьёзного восстановления лучше сначала посмотреть содержимое и решить,
какие части должны быть созданы раньше остальных.

Например:

* пространства имён;
* CRD и операторы, если сохранённые ресурсы от них зависят;
* RBAC и конфигурация;
* PVC;
* рабочие нагрузки;
* Ingress, Service и остальные объекты приложения.

Если CRD ещё нет в новом кластере,
пользовательские ресурсы этого CRD применить не получится.
Сначала должен быть установлен сам оператор или CRD.

## Не запускайте приложение раньше данных

> [!WARNING]
> Опасно сразу применять все Deployment и StatefulSet, если их PVC ещё пустые.
>
> Приложение может:
>
> * создать новую пустую базу;
> * выполнить миграции;
> * изменить структуру каталога;
> * записать новые данные до восстановления старых.

Обычно удобнее сначала создать PVC и базовые ресурсы, вернуть данные,
а затем запускать рабочие нагрузки.

## Контейнерные образы

Если исходный реестр больше недоступен,
сначала опубликуйте сохранённые образы в доступный реестр.

Опубликовать образы из локальной копии можно так:

```shell
kube-dump image push dir ./backup registry.example.com/recovered
```

Опубликовать образы из S3 можно так:

```shell
kube-dump image push s3 registry.example.com/recovered --s3-uri s3://backup/prod/
```

После этого нужно обеспечить,
чтобы восстановленные Pod использовали доступные образы.

Есть два основных подхода.

### Сохранить старые имена

Если можно восстановить прежний адрес реестра через DNS,
зеркало или настройку контейнерного окружения, YAML можно не менять.

### Использовать новый реестр

Если образы опубликованы под новым адресом,
ссылки в YAML нужно изменить до запуска рабочих нагрузок.

Ссылки можно изменить обычными для проекта инструментами:

* через Kustomize;
* через Helm values;
* через GitOps-репозиторий;
* любым инструментом обработки YAML;
* вручную, если окружение небольшое.

kube-dump специально не вводит собственный язык
переназначения образов для восстановления.

Для сложной работы с реестрами можно использовать [ORAS], [crane] или [regctl].

## PVC

kube-dump не создаёт новый PVC автоматически,
но умеет вернуть выбранную копию в уже существующий PVC.

```shell
kube-dump pvc restore dir ./backup \
  --pvc production/postgres-data \
  --target-pvc recovery/postgres-data
```

Для восстановления из S3 выполните:

```shell
kube-dump pvc restore s3 \
  --s3-uri s3://backup/prod/ \
  --pvc production/postgres-data \
  --target-pvc recovery/postgres-data
```

По умолчанию команда требует пустой целевой PVC.
Режимы `merge` и `replace` нужно выбрать явно через `--existing`.
`--revision` выбирает конкретную копию,
если по одному PVC сохранено несколько версий.

Целевой PVC должен быть `Bound`, использовать режим `Filesystem`,
иметь ёмкость не меньше размера распакованных данных
и не должен быть смонтирован работающим Pod'ом.
Для `merge` размер уже занятых данных не определяется через Kubernetes API,
поэтому проверка ёмкости остаётся минимальной.

> [!CAUTION]
> `replace` удаляет существующее содержимое целевого PVC перед записью;
> частичный результат при ошибке потока автоматически не откатывается.

Если автоматическое восстановление не подходит,
содержимое можно получить как обычные файлы.

Например:

```shell
kube-dump pvc extract ./data.tar.zst ./restored
```

Для AGE-зашифрованного архива дополнительно передайте файл с закрытым ключом:

```shell
kube-dump pvc extract ./data.tar.zst.age ./restored \
  --identity ./age-identity.txt
```

Дальше данные нужно перенести в целевой PVC подходящим для среды способом.

## Простой способ вернуть файлы в PVC

Для небольших и средних томов можно создать временный Pod,
который монтирует целевой PVC.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pvc-restore

spec:
  restartPolicy: Never

  containers:
    - name: restore
      image: alpine:3.22
      command:
        - sh
        - -c
        - sleep infinity

      volumeMounts:
        - name: data
          mountPath: /restore

  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: postgres-data
```

Создайте временный Pod:

```shell
kubectl apply -f restore-pod.yaml
```

Затем передайте распакованные файлы в смонтированный PVC:

```shell
tar -C ./restored -cf - . |
  kubectl exec -i pvc-restore -- tar -C /restore -xf -
```

После проверки удалите временный Pod:

```shell
kubectl delete pod pvc-restore
```

Это только простой пример.
Для очень больших томов передача через `kubectl exec` может быть медленной.

## Большие PVC

Для сотен гигабайт и терабайт лучше использовать путь,
который не гоняет весь поток через Kubernetes API.

В зависимости от инфраструктуры это может быть:

* временный Pod или Job, который сам скачивает архив из S3;
* средства копирования самого хранилища;
* CSI-снимки и клонирование томов;
* `rsync` или другой файловый транспорт внутри сети кластера;
* механизм импорта, который предоставляет само приложение.

kube-dump в этом случае остаётся источником переносимой копии данных, а
способ загрузки выбирается под конкретное хранилище.

## Базы данных

Архив PVC - это копия файловой системы.

Если приложение продолжало работать во время создания снимка,
такая копия не обязательно равна логической резервной копии приложения.

Для PostgreSQL, MySQL, ClickHouse, Elasticsearch и других систем
нужно учитывать их собственные правила восстановления.

Если для приложения уже существует надёжный штатный механизм,
например `pg_dump`, `pg_restore`, `mysqldump`, `xtrabackup`
или собственный API резервного копирования,
он может быть предпочтительнее для основной копии базы данных.

PVC-копия при этом остаётся полезным дополнительным уровнем защиты.

## Права и владельцы файлов

При переносе важно сохранить не только содержимое файлов, но и:

* права доступа;
* владельца и группу;
* символические ссылки;
* структуру каталогов.

Особенно это важно для баз данных и приложений,
которые запускаются не от `root`.

Если данные копируются через временный Pod, убедитесь,
что он имеет право восстановить нужные владельцы и режимы доступа.
Архив также сохраняет числовые UID/GID и время изменения файлов и каталогов.
Расширенные атрибуты, ACL, разреженность, устройства
и другие специальные файлы в переносимый контракт не входят.
Восстановление ненулевых UID/GID Windows-агентом не поддерживается.

Вспомогательная служба запускается с правами root,
но получает только необходимые Linux capabilities.
Её эфемерный `/tmp` хранит только небольшие runtime-файлы;
проверка и распаковка потока не создают там копию размером с PVC.
Временные Pod и Lease имеют ограниченный срок жизни.
После прерванного запуска проверьте и удалите оставшиеся объекты
по меткам `app.kubernetes.io/managed-by=kube-dump` и `kube-dump/source-pvc`.

## Другой StorageClass

В новом кластере необязательно использовать тот же StorageClass.

Обычно достаточно:

1. создать новый PVC нужного размера;
1. дождаться его готовности;
1. перенести туда файлы из резервной копии.

Это одна из причин, почему kube-dump хранит PVC как переносимый файловый архив,
а не только как ссылку на CSI-снимок конкретного хранилища.

## Перенос между кластерами

Для переноса можно использовать тот же подход, что и при аварии.

На исходном кластере сохраните данные:

```shell
kube-dump resource save s3 --s3-uri s3://backup/migration/
kube-dump pvc save s3 --s3-uri s3://backup/migration/
kube-dump image save s3 --s3-uri s3://backup/migration/
```

На новом кластере восстановите их в таком порядке:

```text
образы -> новый реестр
ресурсы -> YAML
PVC    -> новые тома
```

После этого приложения запускаются уже в новом кластере.

> [!TIP]
> Перед настоящим переносом лучше один раз пройти весь процесс
> на тестовом окружении.

## GitOps

Если ресурсы уже управляются Argo CD, Flux или другим GitOps-инструментом,
обычно не стоит применять сохранённый YAML поверх него без необходимости.

В таком окружении kube-dump может выполнять другую роль:

* Git остаётся основным источником желаемого состояния;
* kube-dump сохраняет фактическое состояние кластера;
* PVC хранят данные, которых нет в Git;
* `image` сохраняет образы, которые могут исчезнуть из реестра.

При восстановлении сначала возвращаются GitOps-контроллер и его репозиторий,
а сохранённые YAML используются для проверки и восстановления того,
чего в Git не оказалось.

PVC и образы восстанавливаются отдельно.

## Что kube-dump намеренно не делает

В kube-dump нет команды, которая автоматически:

* строит граф зависимостей всех объектов;
* решает порядок установки операторов и CRD;
* создаёт новые PVC и заливает в них данные;
* переписывает все ссылки на контейнерные образы;
* восстанавливает внешние облачные сервисы;
* выполняет миграции конкретной базы данных;
* гарантирует готовность приложения после `kubectl apply`.

Эти задачи сильно зависят от конкретного кластера и приложения.

kube-dump вместо этого сохраняет три вещи,
без которых восстановление часто вообще невозможно:

* конфигурацию;
* данные;
* образы.

и возвращает их в стандартных форматах.

## Проверяйте восстановление заранее

Лучший способ понять, достаточно ли резервной копии -
периодически восстанавливать её в отдельное окружение.

Минимальный сценарий проверки восстановления:

1. Новый тестовый кластер.
1. Новый пустой реестр или отдельный путь в существующем.
1. Пустые PVC.
1. Публикация сохранённых образов.
1. Возврат данных PVC.
1. Применение ресурсов.
1. Проверка приложения.

Так быстро обнаруживаются вещи, которых нет ни в kube-dump, ни в YAML:

* внешние DNS-записи;
* облачные секреты;
* сертификаты;
* зависимости от конкретного StorageClass;
* настройки внешних баз данных;
* недоступные реестры;
* ручные действия, о которых никто не помнил.

Резервная копия, которую никогда не пробовали восстановить,
даёт намного меньше уверенности.
