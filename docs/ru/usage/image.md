# Контейнерные образы

Команда `image` сохраняет образы, которые используют Pod.

Это дополняет YAML и PVC. В манифесте может остаться тег,
но сам образ через некоторое время может исчезнуть из реестра
или тег может начать указывать на другое содержимое.

Полный список параметров находится в [справочнике команд](../../cli.md#image).

## Сохранение

Сохраните образы в локальный каталог:

```shell
kube-dump image save dir ./backup
```

Для сохранения в S3 укажите S3-приёмник:

```shell
kube-dump image save s3 --s3-uri s3://backup/prod/
```

Образы хранятся в стандартном OCI Image Layout:

```text
images/
  oci-layout
  index.json
  blobs/
```

Собственного формата образов kube-dump не вводит.

При повторном сохранении в тот же S3-префикс
уже существующие блобы переиспользуются по digest.
`index.json` публикуется только после успешного завершения захвата.
Операции `image download s3` и `image push s3` читают только граф,
достижимый из этого индекса; старые бесхозные блобы не скачиваются.
Индекс S3 обновляется условно:
параллельные захваты не перезаписывают индекс друг друга молча,
а завершаются явным конфликтом.

Индексы больше 16 МиБ или содержащие
более 100 000 манифестов верхнего уровня отклоняются при проверке.
Это ограничивает объём служебных данных при просмотре и публикации.
При массовой ошибке захвата команда сохраняет подробности
не более чем для восьми образов и сообщает число скрытых подробностей;
счётчик ошибок при этом включает все образы.

## Как определяется нужный образ

kube-dump получает ссылки на образы из следующих полей:

```text
spec.containers[].image
status.containerStatuses[].imageID
```

и на такие же поля init-контейнеров.

`spec.containers[].image` сохраняет исходное имя, например:

```text
ghcr.io/acme/api:mr-123
```

`imageID` позволяет по возможности получить именно тот дайджест,
который реально запущен.

В сохранённом OCI-layout отдельно остаются
исходная ссылка `spec.containers[].image` и дайджест запущенного образа.
Они могут различаться: ссылка описывает объявление Pod,
а дайджест - фактически работавшее содержимое.

> [!WARNING]
> Если точный дайджест использовать нельзя,
> kube-dump пробует исходную ссылку из `spec` и пишет предупреждение.
> Это важно: изменяемый тег к этому моменту уже может указывать на другой образ.

## Пространства имён

```shell
kube-dump image save dir ./backup --namespace production
```

Флаг можно указывать несколько раз.

## Платформы

Без `--image-platform` сохраняется вариант образа,
который используется запущенным контейнером.

Чтобы сохранить дополнительные варианты платформы, перечислите их явно:

```shell
kube-dump image save dir ./backup \
  --image-platform linux/amd64 --image-platform linux/arm64
```

Если у образа отсутствует хотя бы одна запрошенная платформа,
kube-dump завершает захват с ошибкой
и не заменяет предыдущий сохранённый OCI-layout.
Каждый отдельный изменяемый исходный тег разрешается один раз в начале захвата.
Все запрошенные платформы этого тега копируются из зафиксированного результата;
один и тот же тег не запрашивается заново для каждой платформы.

## Доступ к реестрам

По умолчанию используются настройки доступа,
которые уже есть там, где запущен kube-dump.

Дополнительно можно использовать `imagePullSecrets` из Pod:

```shell
kube-dump image save dir ./backup --image-pull-secrets
```

> [!NOTE]
> Это помогает в обычных случаях с Kubernetes Secret,
> но не заменяет все возможные механизмы авторизации kubelet.

Практически это означает следующее:
среда запуска kube-dump сама должна иметь доступ к основным реестрам,
а `--image-pull-secrets` служит дополнительным способом.

## Зеркало реестра

Если исходный адрес нужно заменить зеркалом, укажите соответствие адресов:

```shell
kube-dump image save dir ./backup \
  --registry-mirror registry.old.example=registry.mirror.example
```

Исходная ссылка при этом остаётся известна, а скачивание идёт через зеркало.

## Отбор через профиль

Например, следующий профиль выбирает образы
только из Pod в пространстве имён `production`:

```yaml
apiVersion: kube-dump/v2
kind: Profile

metadata:
  name: production
  description: Production image backup

resources: {}

images:
  selection:
    namespaces:
      - production
```

Можно выбирать Pod по меткам, аннотациям и владельцам,
а сами ссылки на образы - по реестру, пути и тегу.

Следующий профиль выбирает образы только из Pod, которыми владеют Deployment:

```yaml
images:
  selection:
    owners:
      resources:
        - apps/v1/deployments
    containerTypes:
      - container
```

`owners` проверяет цепочку `ownerReferences` Pod, а не имя самого Deployment.
Встроенный image RBAC разрешает чтение
стандартных владельцев из `apps` и `batch`.
Для произвольных ресурсов CRD профилю нужны дополнительные права `get`.

Например, следующий фрагмент ограничивает ссылки на образы:

```yaml
images:
  selection:
    references:
      - registry: ghcr.io
        repository: acme/*
        tags:
          - 'release-*'
```

Полный формат: [справочник профиля](../../profile.md#imagepolicy).

## Просмотр

Посмотрите локальную копию образов:

```shell
kube-dump image inspect dir ./backup
```

Чтобы посмотреть копию в S3, выполните:

```shell
kube-dump image inspect s3 --s3-uri s3://backup/prod/
```

Команда показывает сохранённые ссылки, дайджесты, платформы и объём данных.

## Публикация в другой реестр

Для публикации локальной копии выполните:

```shell
kube-dump image push dir ./backup registry.example.com/recovered
```

Для публикации копии из S3 выполните:

```shell
kube-dump image push s3 registry.example.com/recovered --s3-uri s3://backup/prod/
```

Если нужно опубликовать только часть сохранённых образов,
передайте ссылки после целевого реестра.
Без дополнительных ссылок публикуются все образы:

```shell
kube-dump image push dir ./backup registry.example.com/recovered \
  ghcr.io/acme/api:2.5-rc.11
```

Перед началом публикации все указанные ссылки проверяются.
Опечатка не приводит к частично выполненной публикации.

Целевой реестр указывается явно.
kube-dump не отправляет образы обратно в исходный реестр автоматически.

Для сложного копирования, переназначения тегов,
подписей и других операций лучше использовать [ORAS], [crane] или [regctl].

[ORAS]: https://github.com/oras-project/oras
[crane]: https://github.com/google/go-containerregistry
[regctl]: https://github.com/regclient/regclient
