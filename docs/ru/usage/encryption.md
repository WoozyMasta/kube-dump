# Шифрование

kube-dump умеет шифровать:

* отдельные значения внутри YAML документов;
* архивы с ресурсами Kubernetes;
* архивы с данными дисков из PVC.

Для отдельных YAML полей доступно шифрование AGE и AES-SIV.
А для архивов применяется только AGE.

## Форматы ключей

`kube-dump key generate` создаёт файл с закрытым ключом AGE
во встроенном формате и ключом X25519.
Это единственный формат, который создаёт сама команда,
но не единственный формат, который принимает `kube-dump`.

Поддерживаются следующие ключи AGE:

* встроенный формат AGE X25519: получатель начинается с `age1`,
  а закрытый ключ - с `AGE-SECRET-KEY-1`;
* SSH Ed25519: открытый ключ начинается с `ssh-ed25519`;
* SSH RSA: открытый ключ начинается с `ssh-rsa`.

SSH-ключи используются как получатели AGE на основе SSH.
ECDSA, DSA и другие типы SSH-ключей для этого не подходят.
Для закрытых SSH-ключей поддерживаются обычные
и защищённые парольной фразой ключи Ed25519 и RSA.

Файл, переданный через `--identity`,
может содержать один или несколько закрытых ключей AGE во встроенном формате.
SSH-ключ укажите в отдельном файле в формате PEM или OpenSSH.
Парольную фразу защищённого SSH-ключа передают через
`--identity-passphrase` или `--identity-passphrase-file`.

## AGE

AGE шифрует данные открытым ключом получателя,
а расшифровывает их соответствующим закрытым ключом.

Создайте файл с закрытым ключом AGE:

```shell
kube-dump key generate --output age-identity.txt
```

При создании резервной копии нужен только открытый ключ:

```shell
kube-dump resource save dir ./backup --recipient age1...
```

Для чтения резервной копии передайте закрытый ключ:

```shell
kube-dump resource cat dir ./backup --identity ./age-identity.txt
```

Если файл с закрытым ключом защищён парольной фразой,
передайте её через `--identity-passphrase`
или безопаснее через `--identity-passphrase-file`.

> [!TIP]
> Главный плюс AGE: система, которая создаёт резервную копию,
> может вообще не иметь возможности её расшифровать.

Особенность AGE: при каждом шифровании получается новый шифротекст.
Даже если исходное значение не изменилось, файл будет отличаться.

Для обычных резервных копий это нормально. Для YAML в Git иногда неудобно.

## AES-SIV

AES-SIV даёт детерминированное шифрование.

При одинаковом исходном значении и том же ключе результат не меняется.
Это удобно для Git:
неизменившийся Secret не создаёт лишних изменений после каждого запуска.

Цена этого свойства - более сложное управление ключом.
kube-dump хранит ключ AES-SIV в служебном наборе ключей,
а сам набор защищает AGE.

Для работы с AES-SIV при сохранении нужны AGE-получатель и закрытый ключ,
который может открыть существующий набор ключей.

Пример сохранения с AES-SIV:

```shell
kube-dump resource save dir ./backup \
  --field-encryption aes-siv \
  --recipient age1... \
  --identity ./age-identity.txt
```

## Что выбрать

Выбирайте AGE, если резервную копию создаёт система,
которой нельзя доверить закрытый ключ.
Для сохранения нужен только открытый ключ получателя,
а закрытый ключ нужен только для чтения или расшифровки.
Это простой вариант для архивов,
обмена резервными копиями и большинства сценариев хранения.

Выбирайте AES-SIV для YAML в Git, если важно не создавать лишних изменений.
При одинаковом значении и том же ключе шифротекст остаётся тем же,
поэтому неизменившийся Secret не создаёт новых изменений после каждого запуска.

> [!WARNING]
> AES-SIV не заменяет AGE:
> ключи AES-SIV хранятся в защищённом AGE наборе ключей.
> Поэтому при каждом сохранении с `--field-encryption aes-siv`
> нужен закрытый AGE- или совместимый SSH-ключ,
> который открывает этот набор ключей.

Если процесс резервного копирования не должен получать доступ
к закрытому ключу расшифровки, используйте AGE:
для создания копии достаточно открытого ключа получателя,
а закрытый ключ понадобится при чтении копии.

## Шифрование отдельных полей

Сначала в профиле отмечаются поля, которые подлежат шифрованию:

```yaml
resources:
  rules:
    - name: secret-data
      match:
        resources:
          - core/v1/secrets
      encrypt:
        - .data.*
```

Затем команда задаёт способ шифрования.

Для AGE выполните:

```shell
kube-dump resource save dir ./backup --field-encryption age --recipient age1...
```

В YAML зашифрованное значение будет отмечено специальной меткой AGE:

```yaml
password: !kube-dump/age |-
  ...
```

Для AES-SIV используется другая метка:

```yaml
password: !kube-dump/aes-siv |-
  ...
```

`resource cat` расшифровывает их и выводит обычный YAML:

```shell
kube-dump resource cat dir ./backup --identity ./age-identity.txt |\
  kubectl apply -f -
```

## Расшифровка для редактирования

Можно расшифровать дерево файлов,
изменить значения и затем зашифровать обратно.

```shell
kube-dump resource decrypt dir ./backup ./backup-decrypted \
  --identity ./age-identity.txt
```

При такой операции kube-dump сохраняет специальные метки:

```yaml
password: !kube-dump/age-decrypted MySecretString
password: !kube-dump/aes-siv-decrypted MySecretString
```

Они нужны, чтобы при обратном шифровании не потерять информацию о том,
какой способ использовался для конкретного поля,
а также это не зависит от профиля и позволяет зашифровать обратно те поля,
которые были расшифрованы.

После редактирования зашифруйте дерево обратно:

```shell
kube-dump resource encrypt dir ./backup-decrypted ./backup-encrypted \
  --recipient age1... --identity ./age-identity.txt
```

Шифрование и расшифровка каталога заменяют только подкаталог `resources/`;
остальные элементы верхнего уровня не затрагиваются,
но приватное хранилище ключей `.kube-dump/crypto/` может обновиться.
Эти два управляемых дерева публикуются как единое целое.
Если преобразование было прервано, следующая операция записи
для того же целевого хранилища автоматически восстановит его.
Если во входных данных нет хранилища ключей,
устаревшее хранилище в выходных данных удаляется.
Манифест владения ресурсами копируется без изменений,
поскольку он нужен последующим сохранениям с `--prune`.

## Шифрование архива ресурсов

Архив можно сразу создать зашифрованным AGE:

```shell
kube-dump resource save archive ./backup.tar.zst.age \
  --format tar.zst.age --archive-recipient age1...
```

Готовый архив можно зашифровать отдельной командой:

```shell
kube-dump resource encrypt archive ./backup.tar.zst ./backup.tar.zst.age \
  --recipient age1...
```

Расшифруйте архив отдельной командой:

```shell
kube-dump resource decrypt archive ./backup.tar.zst.age ./backup.tar.zst \
  --identity ./age-identity.txt
```

AES-SIV для целого архива не используется.

## Шифрование PVC

```shell
kube-dump pvc save dir ./backup --recipient age1...
```

Чтобы зашифровать готовый архив PVC, выполните:

```shell
kube-dump pvc encrypt ./data.tar.zst ./data.tar.zst.age \
  --recipient age1...
```

Чтобы расшифровать архив PVC, выполните:

```shell
kube-dump pvc decrypt ./data.tar.zst.age ./data.tar.zst \
  --identity ./age-identity.txt
```

## Несколько получателей

Можно указать несколько открытых ключей:

```shell
kube-dump resource save dir ./backup \
  --recipient age1first... --recipient age1second...
```

Либо передайте файл со списком получателей:

```shell
kube-dump resource save dir ./backup --recipients-file ./recipients.txt
```

Файл содержит по одному получателю на строку.
Пустые строки и строки, начинающиеся с `#`, игнорируются.
В одном файле можно смешивать получатели AGE во встроенном формате
и получатели на основе SSH:

```text
# Получатель AGE во встроенном формате
age1example...

# SSH-получатели
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAA...
ssh-rsa AAAAB3NzaC1yc2EAAAADAQABAAABAQ...
```

Для SSH-строки допустим обычный комментарий после открытого ключа.

> [!IMPORTANT]
> Файл `--recipients-file` содержит только открытые ключи
> и может храниться рядом с конфигурацией или в репозитории.
> Закрытые ключи в него не помещают.

Получателей можно загрузить из внешнего HTTP- или HTTPS-файла:

```sh
kube-dump resource save dir ./backup \
  --recipients-url https://keys.example.com/backup.txt
```

Содержимое URL должно иметь тот же формат, что и `--recipients-file`.
Размер ответа и время ожидания ограничены.

> [!WARNING]
> HTTP не проверяет подлинность источника.
> При перехвате запроса злоумышленник может подменить открытые ключи своими
> и получить доступ к новым зашифрованным копиям.
> Используйте HTTP только в доверенной сети.

Для публичных SSH-ключей пользователя GitHub используйте повторяемый флаг:

```sh
kube-dump resource save dir ./backup \
  --recipient-github-user alice \
  --recipient-github-user bob
```

GitHub-ключи изменяются независимо от kube-dump.
Если пользователь удалит ключ из GitHub,
старые зашифрованные копии по-прежнему потребуют прежний закрытый ключ.

## Обслуживание AES-SIV

Для набора ключей есть две команды.

Чтобы создать новый активный ключ, выполните:

```shell
kube-dump key rotate ./backup \
  --identity ./age-identity.txt --recipient age1...
```

Чтобы заменить AGE-получателей, которыми защищён набор ключей, выполните:

```shell
kube-dump key rewrap ./backup \
  --identity ./old-age-identity.txt --recipient age1new...
```

Эти команды обслуживают ключи и не переписывают автоматически все YAML.
